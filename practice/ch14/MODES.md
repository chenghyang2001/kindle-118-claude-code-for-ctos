# MODES.md — 新專案三種開發模式判斷

> 依 K118《Claude Code for CTOs》第 14 章「新專案」整理。書上把新專案分成 Mode A／B／C，
> 並建議 Mode B／C 走 Scaffold-First。下表的「判斷問題」與「門檻」是本練習整理的，
> 書上沒有給具體數字的地方一律標「假設值」。

## 一、三種模式一覽

| 模式 | 書上定位 | AI 的角色 | 程式碼壽命 | 典型例子 |
| --- | --- | --- | --- | --- |
| **Mode A** | 原型驗證，快速捨棄 | 主力寫手，人只看結果 | 短（驗證完就丟） | 黑客松 demo、測試一個 API 能不能用、給老闆看的 clickable mock |
| **Mode B** | 生產級專案，架構優先 | 在人定好的架構與護欄內填實作 | 長（要上線、要維護） | 新的微服務、對外 API、會有其他工程師接手的 repo |
| **Mode C** | 系統架構設計，AI 為思考夥伴 | 討論對象、提方案、挑毛病；不直接產出主要程式碼 | 產物是決策與文件 | 拆單體、選資料庫、多服務邊界設計 |

## 二、判斷問題清單（依序回答，第一個「是」就停）

1. **這次的主要產出是「決策／架構文件」而不是可執行程式碼嗎？**
   → 是：**Mode C**（AI 當思考夥伴，產出 ADR、架構圖、取捨比較）。
2. **這份程式碼預計會上線、給客戶用，或會被其他人接手維護嗎？**
   → 是：**Mode B**（Scaffold-First）。
3. **做錯了的代價高嗎？（碰金流、個資、權限、資料寫入）**
   → 是：**Mode B**。
4. **預期壽命超過 2 週（假設值），或會超過 1 個人碰它嗎？**
   → 是：**Mode B**。
5. **以上皆否，只是想快速驗證「這個點子／這個套件行不行」？**
   → **Mode A**，並在 README 第一行寫「原型，不得直接上線」。

## 三、模式之間的轉換

- **A → B**：原型證明可行後，**不要**直接在原型上補洞。照書上的 Prototype-to-production 思路：
  把原型當規格參考，重新以 Mode B 的 Step 1（寫 CLAUDE.md）開始。
- **C → B**：Mode C 討論出的決策寫進新專案的 `CLAUDE.md`「架構決策」段落，再進 Mode B。
- **B 中途遇到大架構問題**：暫停實作，切回 Mode C 討論，結論回寫 `CLAUDE.md` 後再繼續。

## 四、Mode B／C 的 Scaffold-First 五步驟（書上版本）

| Step | 內容 | 本練習對應 |
| --- | --- | --- |
| 1 | 寫架構文件 `CLAUDE.md`（決策、約定、What NOT to do） | commit 1 |
| 2 | 只產生目錄、介面、型別、空測試骨架（驗收條件當測試名稱），不准寫業務實作 | commit 2 |
| 3 | 依 PRD 驗收條件補全測試內容，維持紅燈 | commit 3～6（每組先紅） |
| 4 | 在護欄內補實作直到綠燈 | commit 3～6（每組轉綠就 commit） |
| 5 | 從第一天起設定 CI 與監控 | 只寫範本 `ci-template.yml`（本練習不建 repo、不 push） |

## 五、快速自檢表

| 檢查 | Mode A | Mode B | Mode C |
| --- | :---: | :---: | :---: |
| 先寫 CLAUDE.md 架構文件 | 選做 | **必做** | **必做**（記錄決策） |
| 驗收條件寫成測試名稱 | 不用 | **必做** | 不適用 |
| 允許 AI 一次產出整個功能 | 可以 | 不行（一組一組轉綠） | 不行（只產方案） |
| 需要 CI | 不用 | **第一天就要** | 不適用 |
| 程式碼可以直接上線 | **禁止** | 可以（通過 CI 後） | 不適用 |
