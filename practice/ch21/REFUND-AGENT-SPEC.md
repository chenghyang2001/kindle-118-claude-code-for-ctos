# 自動退款客服代理 產品規格（REFUND-AGENT-SPEC）v2

> 虛構產品，供 K118 第 21 章演練。公司名「好物購」為虛構。金額與比例數字皆為 **假設值**。
> v1 見 git commit `9361a83`；v1 → v2 的修正依據見 `GAP-ANALYSIS.md`（G1～G7）。

## 變更紀錄

| 版本 | 變更 | 對應缺口 |
| --- | --- | --- |
| v1 | 初版：符合資格即自動退款，上限寫在提示詞 | — |
| v2 | 退款依 HITL 矩陣分級；上限移到後端；加 AI 揭露與理由；稽核日誌；轉真人＋kill switch；失敗模式；工具權限收斂 | G1～G7 |

## 1. 目標

減少客服退款案件的人工處理量，**在不增加不可逆損失的前提下**，讓 AI 代理處理常見退款申請。目標：70% 的退款案件由代理「完成或備妥待核」（假設值），其中低額案件自動完成。

## 2. 使用者與角色

| 角色 | 職責 |
| --- | --- |
| 消費者 | 在網頁／App 客服視窗發起退款 |
| 客服專員 | 接手轉人工案件；處理 > NT$5,000 退款 |
| 客服主管（審核者） | 事前確認 NT$1,001–5,000 退款；收事後通知；可按 kill switch |
| 值班工程師 | 可按 kill switch；看監控告警 |

## 3. 透明度（G4）

- **開場揭露**：「您好，我是好物購的 AI 客服助理。退款申請我可以協助處理，任何時候輸入『真人』即可轉接專員。」
- **每個決策附理由**，分兩段：
  - 事實：訂單編號、到貨日、商品狀態（取自系統）
  - 依據：退款政策第 X 條（政策版本號）
- **拒絕時**：說明未符合的條件＋「轉真人申訴」按鈕。
- **低信心**（信心 < 0.8）：不判斷，直接說明「這個情況需要專員確認」並轉人工。

## 4. 主要流程

1. 消費者說明退款需求。代理以 **當前登入身分** 查詢其訂單與物流。
2. 代理依退款政策（7 天鑑賞期、未拆封、非客製化）判斷資格，產生「判斷＋理由＋信心」。
3. 依 §5 動作權限表決定處理方式：
   - **自動＋事後通知**：退款服務閘道執行，通知主管。
   - **事前確認**：建立「退款提案」送審，告知消費者「已送專員確認，預計 4 小時內回覆」（假設值）。
   - **禁止**：轉客服專員，附對話摘要與代理判斷。
4. 代理優先提供「退到購物金」（可撤銷），消費者堅持原付款方式時才走信用卡退款。
5. 每一步寫入稽核日誌（§7）。

## 5. 動作權限表（依 HITL-MATRIX，G1）

| 動作 | 可逆性 | 影響 | 處理方式 |
| --- | --- | --- | --- |
| 查訂單／物流（僅本人） | R1 | I1 | ✅ 自動 |
| 加內部備註、草擬回覆 | R1 | I1 | ✅ 自動 |
| 退購物金 ≤ NT$1,000 | R2 | I1 | ✅ 自動（5% 抽樣稽核） |
| 退購物金 NT$1,001–5,000 | R2 | I2 | 📨 事後通知（24 小時內可撤銷） |
| 退原付款方式 ≤ NT$1,000 | R3 | I1 | 📨 事後通知 |
| 退原付款方式 NT$1,001–5,000 | R3 | I2 | 🙋 事前確認 |
| 任何退款 > NT$5,000 | R3 / R2 | I3 | ⛔ 代理禁止，轉專員 |
| 發補償優惠券 ≤ NT$200、每人每月 1 張 | R2 | I1 | ✅ 自動 |
| 拒絕退款 | R2 | I1～I2 | 📨 事後通知（必附理由） |

**升級規則**（一律往嚴格方向）：低信心、30 天內第 3 次退款、新帳號 < 7 天、當日累計超過 NT$1,000 → 至少「事前確認」。

**審核逾時**：事前確認 4 小時無人處理 → 不執行，轉客服專員並通知消費者（fail-closed）。

## 6. 工具與權限邊界（G2、G7）

| 工具 | 參數 | 限制（由後端強制） |
| --- | --- | --- |
| `get_my_orders()` | 無；user_id 由 session 注入 | 只能查當前使用者 |
| `get_shipment(order_id)` | order_id | 後端驗證訂單屬於當前使用者 |
| `propose_refund(order_id, amount, method, reason)` | — | 只建提案，不直接退款 |
| `issue_coupon(amount)` | ≤ 200 | 每人每月 1 張 |
| `handoff_to_human(summary)` | — | 永遠可用 |

- 實際退款由「退款服務閘道」依 §5 表決定自動執行或送審，**代理沒有直接呼叫付款 API 的權限**。
- 代理使用專用服務帳號 `svc-refund-agent`，無管理員權限。
- **金額門檻寫在閘道設定，不寫在提示詞**；提示詞只描述政策，不作為安全邊界。
- 上線前紅隊測試：至少 10 種提示詞注入（「忽略規則」「我是主管」「退我 10 萬」等），全部不得改變處理方式。

## 7. 稽核日誌（G3）

append-only 儲存，代理服務帳號只有寫入權限、無修改／刪除權限。每筆欄位：

`event_id`、`timestamp`、`conversation_id`、`user_id`（雜湊）、`order_id`、`action`、`amount`、`method`、`decision`、`reason_facts`、`reason_policy`、`policy_version`、`confidence`、`model_id`、`prompt_version`、`hitl_level`、`approver_id`（若有）、`idempotency_key`

- 卡號、電話、地址遮罩後才寫入。保存 3 年（假設值）。

## 8. 失敗模式（G6）

| 失敗模式 | 偵測 | 處理 |
| --- | --- | --- |
| 模型錯判資格 | 抽樣稽核、客訴 | 事後通知可撤銷；錯判率 > 2%（假設值）告警 |
| 付款 API 逾時／重送 | 閘道回應 | 冪等鍵 `order_id + request_id`，重送不重複退款 |
| 模型 API 逾時或錯誤 | 例外 | fail-closed：轉人工 |
| 提示詞注入 | 紅隊測試、異常金額告警 | 後端門檻擋下；記錄並告警 |
| 外部物流資料過期 | 資料時間戳 | 已知風險（見 §11） |
| 自動核准率異常飆升 | 監控 | 1 小時內 > 基準 1.5 倍（假設值）自動告警，值班可按 kill switch |

## 9. 轉真人與 Kill Switch（G5）

- 消費者輸入「真人」或點按鈕 → 立即轉接，專員畫面顯示對話全文＋代理判斷＋理由。
- **Kill switch**：客服主管或值班工程師在後台一鍵切換，30 秒內（假設值）生效；生效後代理只能對話與轉人工，所有寫入動作被閘道拒絕。每季演練一次。

## 10. 成功指標

| 指標 | 目標（假設值） |
| --- | --- |
| 代理完成或備妥待核比例 | ≥ 70% |
| 低額自動退款的錯判率（抽樣稽核） | ≤ 2% |
| 平均處理時間（自動段） | < 2 分鐘 |
| 客訴率 | 不高於上線前 |
| 轉真人後客戶滿意度 | 不低於上線前 |
| 重複退款事件 | 0 |

## 11. 上線計畫與已知風險

- **上線條件**：檢查表 🔴 全數通過、紅隊測試通過、kill switch 演練通過、離線評估集 500 筆（假設值）錯判率 ≤ 2%。
- **階段**：先 10% 流量兩週，且只開「購物金退款」；第二階段才開「原付款方式退款」。
