# SANDBOX-PROJECTS.md — 試點沙盒專案候選

> 書上第 6 章：沙盒專案要選 2–3 個「有真實業務價值」的專案，而不是玩具題目——玩具題目做得再好也說服不了懷疑者。
> 以下三個候選以一間假想 SaaS 公司為背景（**情境為假設**），評分權重亦為**假設值**。

## 挑選評分標準

| 準則 | 權重（假設值） | 5 分 | 1 分 |
| --- | --- | --- | --- |
| A. 真實業務價值 | 25% | 完成後有人每天用、或能還掉明確技術債 | 做完沒人在乎 |
| B. 低爆炸半徑 | 25% | 出錯不影響正式客戶、可隨時回滾 | 直接碰金流／個資／正式 DB |
| C. 可驗證性 | 20% | 有測試或明確驗收條件，對錯一眼可判 | 只能靠主觀感覺 |
| D. 規模適中 | 15% | 1–3 週可交付，跨 2–10 個檔案 | 一天做完或要做一季 |
| E. 學習覆蓋面 | 15% | 能練到計畫模式、審 Diff、寫 CLAUDE.md、測試生成 | 只練到單一技巧 |

總分 = Σ（分數 × 權重），滿分 5.0。**≥ 3.8 才入選**（假設值）。
一票否決：涉及正式環境寫入、客戶個資、金流核心邏輯者，不論總分一律不選。

## 候選 1：為缺乏測試的「報表匯出模組」補單元測試

- **內容**：既有 CSV/Excel 匯出模組覆蓋率低，讓 Claude 讀程式碼、產生單元測試，人類審查測試是否真的有斷言意義。
- **業務價值**：客服每月收到匯出格式錯誤的抱怨；補測試後重構才有安全網。
- **為何適合**：書上第 4 章把「單元測試生成」列為高回報任務（可提升 30–60% 效率）。只新增測試檔，不改正式邏輯，爆炸半徑最小。
- **評分**：A4 / B5 / C5 / D4 / E3 → **4.30** ✅

## 候選 2：內部後台「功能旗標管理頁」

- **內容**：目前功能旗標靠工程師手改設定檔，做一個只給內部使用的 CRUD 頁面（沿用既有 Layout 元件與 API 慣例）。
- **業務價值**：PM 可自行開關實驗功能，減少工程師被打斷次數。
- **為何適合**：完整走過 PRD → 計畫模式 → 實作 → Agent 預審 → 同儕審查，正好對應 Week 3「交付完整功能」；僅內部使用，可加權限保護。
- **評分**：A4 / B4 / C4 / D4 / E5 → **4.15** ✅

## 候選 3：舊版 API Client 的漸進式遷移（單一服務）

- **內容**：把一個非核心服務（例如通知服務）從自寫的 HTTP 包裝層遷移到團隊標準 client，保持公開 API 不變。
- **業務價值**：消除重複的重試／逾時邏輯，降低後續維護成本。
- **為何適合**：典型「樣板與遷移」任務，適合 Week 2 的小規模重構；有既有整合測試可驗證行為不變。
- **風險**：碰到網路行為，需在 staging 驗證，B 項分數較低。
- **評分**：A4 / B3 / C5 / D4 / E4 → **3.95** ✅（C 項給 5 分：既有整合測試可直接驗證行為不變；排第三順位）
