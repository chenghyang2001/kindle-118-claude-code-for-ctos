# FAQ.md — Claude Code 導入常見問題

> 第 6、10 章建議：把試點期的常見困惑整理成 FAQ，放在 repo 裡隨規範演進。標「（假設值）」者為本練習自訂。

### Q1. Claude 會不會亂改我們的程式碼？

可以先完全不讓它寫。書上給懷疑者的做法：用 `--permission-mode`（例如 `plan`）限制成唯讀分析，確認它理解程式碼後再開放寫入。專案層 `.claude/settings.json` 的 deny 規則會擋下 `rm -rf`、`curl | bash`、修改 `.env*` 等操作。

### Q2. 導入初期效率變差是正常的嗎？

正常。書上第 4 章估計前兩週生產力約下降 10–15%，之後才回升。主管應事先說明此期間不列入績效。

### Q3. 需要多少訓練時間？

書上估計每人 2–4 小時的正式訓練，加上四週漸進式導入路徑（Observe → Assist → Lead → Teach）。

### Q4. 哪些任務適合交給 Claude？哪些不適合？

適合：單元測試、樣板程式碼、資料庫遷移腳本、有清楚慣例可循的重構（書上列為高回報任務）。
不適合直接交出去：從零設計 DB Schema、安全／權限架構決策、需求本身還模糊的工作——這些保留人類主導。

### Q5. `CLAUDE.md` 要寫多長？誰負責維護？

寫「Claude 不讀就會猜錯」的東西：架構決策、命名與錯誤處理慣例、測試指令、明確的「不要做」清單。所有人都能提 PR 修改，Week 3 每位試點成員至少貢獻一個章節。篇幅建議控制在 200 行內（假設值），太長會被稀釋。

### Q6. Claude 產生的程式碼要怎麼審查？

和人寫的一樣嚴格，甚至更嚴。流程：Agent 預審（請 Claude 依 `CLAUDE.md` 自審並「Be critical」）→ 人類逐行審 Diff → CI。不能只看「測試通過」，要確認測試本身有意義。

### Q7. 可以用 `--dangerously-skip-permissions` 加快速度嗎？

只能在受控的 CI 或拋棄式沙盒環境使用，絕不在開發者本機或碰得到正式資源的環境使用。

### Q8. 我們有我的個人設定、團隊設定，該放哪裡？

團隊共用的規則（權限、hooks、MCP）放專案層 `.claude/settings.json` 並進版控；個人偏好放 `.claude/settings.local.json`（不進版控）。新增 MCP 一律用 `--scope project`，讓全隊一致。

### Q9. 遇到問題要問誰？

先查本 FAQ 與 `ANTI-PATTERNS.md`，再到 `#claude-code` 頻道發問。每週 30 分鐘 Insight-sharing 會議會把高頻問題補進本文件。

### Q10. 我不相信 AI，可以不參加嗎？

試點本來就刻意納入健康懷疑者。你的工作不是「被說服」，而是找出它在哪裡會出錯——這些紀錄會直接變成 ANTI-PATTERNS 與 deny 規則。

### Q11. 怎麼知道導入有沒有成功？

四週結束看 Go/No-Go 指標（見 `ROLLOUT.md`）：完成率、回滾數、推薦意願，以及穩定後的效率提升（書上以 20% 為基準，保守 15%、樂觀 30%）。
