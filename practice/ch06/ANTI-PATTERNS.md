# ANTI-PATTERNS.md — Claude Code 團隊導入反模式

> 每條含「徵兆」（怎麼發現）與「對策」（怎麼修）。書上明確提到者標【書】，其餘為本練習整理的常見情況。

## 1. 讓 AI 從頭設計資料庫 Schema【書】

- **徵兆**：PR 裡出現大量新 table／欄位，描述只寫「Claude 建議的結構」；沒人能說出某欄位為何存在。
- **對策**：Schema 由人類設計並寫成 ADR，Claude 只負責依既定設計產生 migration 與測試。在 `CLAUDE.md` 的「不要做」清單明列。

## 2. 只看 CI 綠燈就合併

- **徵兆**：審查時間急遽縮短；PR 評論只有「LGTM」；上線後出現「測試都過了怎麼會壞」。
- **對策**：要求人工逐行審 Diff 並檢查測試斷言是否有意義；Week 2 完成標準就包含審查紀錄。

## 3. 模糊提示詞，期待讀心

- **徵兆**：提示詞像「幫我做一個 dashboard」；Claude 產出風格與既有程式碼不一致，反覆來回修改。
- **對策**：用書上的「精確意圖」寫法：指定要沿用的元件、資料來源方法、參考檔案、載入與錯誤狀態。功能級任務先寫 PRD 五區塊。

## 4. 跳過計畫模式直接動手

- **徵兆**：大改動一次改十幾個檔案，事後才發現方向錯；revert 頻率高。
- **對策**：跨模組任務一律先以計畫模式產出「要改哪些檔案、為什麼」，人類同意後才執行。

## 5. 全員一次性導入（Big Bang）

- **徵兆**：週一全公司開通，週三頻道充滿抱怨，兩週後使用率掉回個位數。
- **對策**：照書上做法，先 3–5 人試點 + 四週漸進路徑，通過 Go/No-Go 再擴大。

## 6. 試點只挑熱衷者

- **徵兆**：試點報告一片好評，但擴大推廣時遭遇強烈抵抗，懷疑者的問題從未被處理。
- **對策**：試點刻意納入健康懷疑者【書】，把他們的質疑轉成 FAQ 與 deny 規則。

## 7. 沙盒選玩具題目

- **徵兆**：試點做的是 Todo App 或 hackathon 題目；主管問「所以對產品有什麼幫助？」答不出來。
- **對策**：沙盒必須有真實業務價值【書】，依 `SANDBOX-PROJECTS.md` 評分標準挑選。

## 8. CLAUDE.md 寫一次就放著

- **徵兆**：`CLAUDE.md` 最後修改是三個月前；Claude 反覆犯同一個錯，大家只在頻道抱怨。
- **對策**：每次 Claude 犯「規範內就能避免的錯」→ 立刻補一條進 `CLAUDE.md`；Week 3 每人須貢獻一章；Insight-sharing 會議固定收集改進建議【書】。

## 9. 本機開 `--dangerously-skip-permissions` 圖方便

- **徵兆**：shell history 出現此旗標；有人說「每次都要按允許太煩」。
- **對策**：此旗標僅限受控 CI／拋棄式沙盒【書】。改用專案層 `permissions.allow` 白名單減少提示（如 `Bash(npm run *)`）。

## 10. 設定散落在個人全域設定

- **徵兆**：「在我電腦上 Claude 會跑 lint，你的不會」；MCP 只有某人裝了。
- **對策**：團隊規則一律放專案層 `.claude/settings.json` 進版控；MCP／plugin 一律 `--scope project`。

## 11. 把審查意見原封丟回給 Claude

- **徵兆**：PR 修正 commit 訊息全是「address review comments」，但修法和審查者意圖不符，來回好幾輪。
- **對策**：作者先自己理解並決定怎麼改，再指示 Claude；Week 3 完成標準要求「自己處理同儕審查」。

## 12. 用 AI 產出量當 KPI

- **徵兆**：週報統計「本週 Claude 產生 N 行程式碼」；PR 越來越大、審查品質下降。
- **對策**：量測結果而非產量：週期時間、回滾數、缺陷率、開發者滿意度。
