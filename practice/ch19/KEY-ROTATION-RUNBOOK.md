# KEY-ROTATION-RUNBOOK.md — Anthropic API 金鑰輪替 SOP

> 書上要求建立「API 金鑰定期輪替 SOP Runbook」（[11]），但沒有給頻率等數字；**以下數字皆為假設值**，請依公司資安政策調整。

## 0. 範圍與角色

| 項目 | 內容 |
| --- | --- |
| 適用金鑰 | Anthropic Console 各工作區發出的 API Key（CI、Agent SDK、內部工具用） |
| 不適用 | 個人 Pro/Max 訂閱 OAuth 憑證（個人自行管理，且不得用於 CI） |
| 負責人 | 金鑰擁有者（Owner）：各團隊 Tech Lead；核准者：資安（CISO 代理人） |
| 金鑰存放 | 只放 Secret Manager／CI Secret，變數名 `ANTHROPIC_API_KEY`（見 `env.example`） |

## 1. 輪替頻率（假設值）

| 情境 | 頻率 |
| --- | --- |
| 一般 CI / 內部工具金鑰 | 每 90 天（假設值） |
| 高權限或多人可存取的金鑰 | 每 30 天（假設值） |
| 人員離職、角色異動 | 24 小時內（假設值） |
| 疑似外洩 | **立即**，走第 5 節緊急撤銷 |

建議每把金鑰命名含建立日期，例：`ci-review-2026-10`，方便看出年齡。

## 2. 例行輪替步驟（雙金鑰零停機）

1. **盤點**：列出這把舊金鑰被哪些地方使用（CI Secret、Secret Manager、部署設定）。
2. **建立新金鑰**：在同一個 Console 工作區建立新 Key，名稱帶新日期。
3. **更新 Secret**：把新值寫入 Secret Manager／CI Secret（不貼進聊天、不寫進檔案、不 commit）。
4. **重新部署／觸發**：重跑使用該金鑰的 pipeline 或重啟服務，讓新值生效。
5. **觀察期**：新舊金鑰並存 24 小時（假設值），在 Console 確認新金鑰有用量、舊金鑰用量歸零。
6. **停用舊金鑰**：在 Console 停用（disable）舊 Key。
7. **再觀察**：停用後 24 小時（假設值）無錯誤 → 刪除舊 Key。
8. **紀錄**：在變更單記錄日期、執行人、金鑰名稱（**不記錄金鑰值**）。

## 3. 驗證

- [ ] 使用新金鑰的 CI job 成功跑完一次。
- [ ] Console 用量頁面顯示新金鑰有呼叫、舊金鑰歸零。
- [ ] 錯誤率／401 數量沒有上升（看 SIEM 或 CI log）。
- [ ] 版本庫掃描無金鑰字串（例：執行 `python check_templates.py`，以及 secret scanning）。

## 4. 回滾

| 狀況 | 回滾動作 |
| --- | --- |
| 新金鑰部署後大量 401 | 舊金鑰尚未停用 → 把 Secret 改回舊值、重新部署 |
| 舊金鑰已停用但仍有服務依賴 | 在 Console 重新啟用（re-enable）舊金鑰（若尚未刪除），補齊遺漏的部署點後再重做第 6 步 |
| 舊金鑰已刪除 | 無法回滾 → 立即把新金鑰補到遺漏處；這就是第 2 步第 7 點要「先停用再刪除」的原因 |

## 5. 事故時緊急撤銷（疑似外洩）

1. **立即停用**外洩金鑰（不等觀察期），目標 15 分鐘內完成（假設值）。
2. 建立新金鑰並更新所有 Secret，接受短暫中斷。
3. 檢查 Console 用量，找出外洩後的異常呼叫（時間、量、來源）。
4. 若金鑰曾被 commit：從 Git 歷史清除只是補救，**撤銷才是止血**；同時開資安事件單。
5. 通知 CISO 與財務（支出可能異常），必要時暫時調低工作區硬性支出上限。
6. 事後檢討：外洩途徑、為何沒被掃描擋下、要補哪個控制點。

## 6. 預防措施

- `.env` 列入 `.gitignore`；只提交 `env.example`。
- pre-commit／CI 加 secret scanning（`check_templates.py` 示範檢查 `sk-ant-` 開頭的值）。
- 每個工作區設硬性支出上限，讓外洩的損失有上限。
