# CONTEXT-PLAYBOOK：大規模脈絡管理守則

> K118《Claude Code for CTOs》第 15 章演練產出。給團隊在中大型 repo 用 Claude Code 時共用。
> 本文中書上沒有給的門檻數字都標「假設值」，團隊可依實測調整（本資料夾的 `COMPARE.md` 是一次實測）。

## 1. 一任務一 session

**規則**：一個 session 只做一件可驗收的事（一張 ticket、一個 bug、一個重構）。做完就收，下一件事開新 session。

為什麼：脈絡視窗是共用資源，前一件事讀進來的檔案、試錯過程、放棄的方案，都會留在後一件事的脈絡裡，變成雜訊，模型還可能沿用已經不成立的假設。

做法：

- 開工第一句話寫清楚「這個 session 的完成條件」（例：`npm test` 全過、PR 描述寫好）。
- 中途冒出別的需求 → 記在 `TODO.md` 或 issue，不要順手做。
- 要平行做多件事 → 每件事開自己的 git worktree + 自己的 session，不要共用工作目錄。
- 收工前讓 Claude 寫一段交接摘要（改了什麼、還沒做什麼），下一個 session 用它開場。

## 2. 顯性前置載入（Explicit Preloading）

**規則**：你已經知道答案在哪裡，就直接告訴 Claude，不要讓它自己找。

提示詞要包含：

| 項目 | 範例 |
| --- | --- |
| 要讀／改的檔案路徑 | `app/src/models/order.js`、`app/test/order.test.js` |
| 型別與介面 | `@property {'low'\|'normal'\|'high'} [priority]` |
| 要新增的函式／路由名稱 | `listByPriority(priority)`、`GET /orders/priority/:priority` |
| 連帶要改的地方 | 「router.test.js 的路由總數 40 → 41」 |
| 驗證指令與完成條件 | 「在 app/ 跑 `npm test` 全過」 |
| 明確的範圍限制 | 「不要讀或搜尋其他檔案」「不要 commit」 |

效果：少掉 Glob／Grep／試讀不相關檔案的探索回合，token 與時間都下降，改動範圍也比較可預期。實測數字見 `COMPARE.md`。

不知道在哪裡時：先開一個**唯讀的探索 session**（或用 Explore subagent）找出檔案清單，再把清單貼進新的實作 session。探索的雜訊留在探索 session，不污染實作 session。

## 3. 三個檔案以上強制 Plan 模式

**規則**：預估會動到 **3 個以上檔案**（門檻：假設值，依書上「多檔改動先規劃」精神訂定）時，先用 Plan 模式（`Shift+Tab` 切換，或 `--permission-mode plan`），計畫確認後才動手。

計畫至少要列出：

1. 要改的檔案清單與每個檔案的改動摘要
2. 改動順序（例：model → service → route → test）
3. 驗證方式（哪些測試、哪個指令）
4. 不會碰的範圍

為什麼：多檔改動最常出錯的是「漏改一個地方」（像本次實驗裡 router.test.js 的路由總數）。先看計畫，花一回合就能抓到；寫完才發現，要多花好幾回合來回修。

## 4. 何時 /compact

`/compact` 會把目前對話摘要壓縮，**同一件事繼續做**，但釋放空間。可加指示：`/compact 保留：改動的檔案清單、目前測試失敗的訊息`。

用 /compact 的判斷訊號：

| 訊號 | 說明 |
| --- | --- |
| 任務還沒做完，但脈絡用量 > 70%（假設值） | 狀態列或 `/context` 可看用量；等自動壓縮時常已太擠 |
| 剛完成一個大階段（例：探索完、計畫定案） | 階段性的大量讀檔輸出已不需要原文 |
| 對話裡有大量長輸出（測試 log、大檔內容）已經處理完 | 原文沒用了，只需要結論 |
| 回應變慢、開始重複讀同一個檔 | 脈絡太長的徵兆 |

壓縮前：把關鍵決策寫進檔案（計畫 MD、TODO），不要只依賴摘要。

## 5. 何時 /clear

`/clear` 清空整個對話，**等同重新開始**。

用 /clear 的判斷訊號：

| 訊號 | 說明 |
| --- | --- |
| 換了一件不相關的任務 | 一任務一 session 的直接結果 |
| 模型被錯誤假設帶偏，修了兩三輪還在繞（次數：假設值） | 壞脈絡比沒脈絡更糟，直接重來並把正確前提寫進新提示詞 |
| 前面試過的失敗方案一直被拿回來用 | 脈絡裡的失敗紀錄在誤導模型 |
| 任務已完成並 commit | 下一件事乾淨開始 |

/clear 前：先讓 Claude 輸出一段交接摘要（或寫進 `HANDOFF.md`），新對話開頭貼回去，等於「手動做的高品質 compact」。

## 6. 決策流程（速查）

```
新需求進來
  ├─ 跟目前 session 的任務無關？ → /clear（或開新 session / 新 worktree）
  ├─ 會動到 ≥ 3 個檔案？         → 先 Plan 模式，計畫確認後再做
  ├─ 知道要改哪些檔？            → 前置載入：路徑 + 型別 + 驗證指令 + 範圍限制
  │    └─ 不知道？              → 先開唯讀探索 session 找清單
  └─ 做到一半脈絡快滿？
       ├─ 方向正確 → /compact（附保留指示）
       └─ 方向歪了 → 寫交接摘要 → /clear → 帶正確前提重來
```

## 7. 團隊落地建議

- 把本守則放進 repo，並在專案 `CLAUDE.md` 用一行引用，讓每個 session 都看得到。
- 常見任務（加欄位、加 API）寫成提示詞範本（見 `prompts/a-preload.md`），套用時只換檔名與欄位。
- 定期用本資料夾的 `scripts/run-ab.sh` + `scripts/stats.js` 在自家 repo 上量一次，用實測數字取代假設值。
