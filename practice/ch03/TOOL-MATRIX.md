# TOOL-MATRIX：AI 編碼工具評估矩陣

> K118《Claude Code for CTOs》第 3 章「市場全景」演練產出。
> 書上的分類：**Vibecoding 工具**（原型驗證為主，如 Lovable）與 **Agentic Coding 工具**（生產級工程，如 Claude Code）。
> 書上的立場：技術領導者應依 **企業控制、成本可預測性、多檔案推理能力** 選工具，而非個人偏好。

## 0. 先講清楚的前提

- **評分全部是「假設值」**：書上第 3 章沒有給各工具的分數，以下 1–5 分是本演練依公開產品定位做的判斷，正式選型前要用自家 repo 實測（見第 4 節）。
- 評分：**5 = 最好**（對「成本」軸代表最可預測，不是最便宜）。
- 書上明列的三軸標 📘；其餘四軸是本演練補的，標 ➕（對應書上「等」字，以及第 8 章稽核六大面向與第 9 章資安治理）。
- 產品功能變動快，本表為 2026-10 的評估快照，每季重評一次。

## 1. 受評工具

| 類別 | 工具 | 典型使用者 | 典型產出 |
| --- | --- | --- | --- |
| Vibecoding | Lovable | PM、設計師、創辦人 | 可點的全端原型（常搭 Supabase） |
| Vibecoding | Bolt | PM、前端、黑客松 | 瀏覽器內生成並跑起來的 Web App |
| Agentic Coding | Claude Code | 工程師、CI 流程 | 在既有 repo 內跨檔案修改＋跑測試＋自我修正 |
| Agentic Coding | Cursor（agent 模式） | 工程師 | IDE 內跨檔案修改，人在迴圈中逐步確認 |

## 2. 評估矩陣（每格：分數｜一句理由）

| 評估軸 | Lovable | Bolt | Claude Code | Cursor agent |
| --- | --- | --- | --- | --- |
| 📘 企業控制（權限、設定、稽核） | 2｜程式碼與執行環境在供應商平台上，能管的多是帳號層級，難套用公司的權限與稽核規則 | 2｜同樣是託管式瀏覽器環境，難限制它能碰什麼、也難留存操作紀錄 | 5｜有專案層 `settings` 的 allow／deny、hooks、`CLAUDE.md` 規範，能把治理規則寫進 repo 裡版控 | 4｜有規則檔與團隊管理，但治理多綁在 IDE 設定，進 CI／無人值守流程較弱 |
| 📘 成本可預測性 | 3｜訂閱價固定，但點數／訊息額度用完要加購，原型反覆修改時花費會跳 | 3｜以 token 額度計，大型專案重生成很吃額度，月底難估 | 4｜可走固定月費方案（書上第 4 章：每人每月 $100–200），但走 API 計費時用量隨任務大小浮動 | 4｜席位月費固定，進階模型或超額請求另計，整體仍好預估 |
| 📘 多檔案推理能力 | 2｜擅長從零生成，但改既有大型程式碼時常顧此失彼、破壞先前功能 | 2｜專案一變大，上下文就不夠，跨檔重構容易不一致 | 5｜原生走 Observe→Plan→Act→Verify 迴圈，可讀整個 repo、跨檔改、跑測試再修 | 4｜跨檔改動能力強，索引整個 codebase，但長任務較依賴人逐步引導 |
| ➕ 生產就緒度（測試、架構、資料模型） | 1｜產出常缺測試、缺 migration、密鑰處理鬆散，正是書上第 8 章稽核的典型對象 | 1｜偏「能跑就好」，架構與測試需事後補 | 4｜品質取決於 `CLAUDE.md` 與測試防護網，有 Harness 時可穩定產出生產級程式碼 | 4｜同樣取決於規範與審查，人在迴圈中有助於維持品質 |
| ➕ 資安與合規 | 2｜程式碼與資料在第三方平台，需另做供應商審查；常見寫死密鑰 | 2｜同上，且瀏覽器環境較難掃描與控管機密 | 4｜程式碼留在自家環境，可用 deny 規則擋 `.env`／`secrets`，但仍需審查資料送往模型的流向 | 4｜程式碼在本機，有隱私模式，但外掛與擴充套件需另行控管 |
| ➕ 可維護性與可攜性 | 2｜可匯出到 GitHub，但產出的結構常需大改才能接手 | 2｜可下載程式碼，但耦合平台慣例，接手成本高 | 5｜直接在團隊自己的 repo、分支、CI 上工作，無平台綁定 | 4｜程式碼在自家 repo，但工作流程綁 IDE |
| ➕ 上手速度（非工程師） | 5｜用自然語言幾分鐘做出可點的畫面，非技術人員也能用 | 5｜瀏覽器開了就能用，零安裝 | 2｜終端機工具，需懂 git、測試與專案結構 | 3｜IDE 介面較親切，但仍是寫程式的工具 |
| **小計（35 分）** | **17** | **17** | **29** | **27** |

> 小計只是加總參考，**不是選型依據**。不同軸對不同用途權重不同（見第 3 節）。

## 3. 選型建議

### 3.1 一句話結論

**Vibecoding 工具用來「驗證想法」，Agentic Coding 工具用來「建造產品」；兩者不互相取代，中間靠 `HANDOFF-POLICY.md` 交接。**

### 3.2 依用途選

| 用途 | 建議工具 | 理由 |
| --- | --- | --- |
| PM／設計師做可點擊原型、驗證需求 | Lovable 或 Bolt | 上手速度最重要，原型做完即丟（對應書上第 14 章 Mode A） |
| 黑客松、一週內的概念驗證 | Bolt 或 Lovable | 零安裝、快速出畫面 |
| 既有生產 repo 的功能開發與重構 | Claude Code（主）＋ Cursor agent（輔） | 多檔案推理與企業控制是關鍵 |
| CI／無人值守批次任務（遷移、測試補齊） | Claude Code | 可寫專案層 settings＋hooks 治理，適合非互動執行 |
| 工程師日常互動式編碼 | Cursor agent 或 Claude Code | 依個人工作流程，兩者都可以，團隊統一規範檔即可 |
| 任何要上線、處理客戶資料的東西 | **不可**直接用 Vibecoding 產出 | 必須先通過 `HANDOFF-POLICY.md` 的交接檢查 |

### 3.3 依公司規模（呼應書上第 1 章四種 CTO 原型）

| 規模 | 建議組合 | 備註 |
| --- | --- | --- |
| Solo CTO | Claude Code 一套就好；需要給投資人看畫面時才用 Lovable | 頻寬是瓶頸，不要同時維護多套工具 |
| Small Team | Claude Code 為標準工具＋允許 PM 用一套 Vibecoding 工具 | 先統一 `CLAUDE.md`，避免做法分歧 |
| Mid-Size | Claude Code＋Cursor 並存，治理規則集中在 repo 內 | 指定工具負責人，每季重評矩陣 |
| Scaling | 以企業控制分數最高者為標準，Vibecoding 工具列白名單、限原型用途 | 需供應商資安審查與採購流程 |

### 3.4 選型時的禁忌

1. 不要因為「某位資深工程師喜歡」就全公司導入——書上明說要看企業控制、成本與多檔案推理。
2. 不要用 Vibecoding 工具的 demo 速度，去估生產級專案的時程。
3. 不要讓原型直接上線——沒有交接規範，原型的技術債就會變成生產事故。

## 4. 正式選型前的實測方法（本演練未執行）

1. 挑一個自家 repo 的真實任務（例如：跨 5 個以上檔案的重構）。
2. 每個工具跑同一個任務，記錄：改了幾個檔、測試是否全過、花了幾回合、花了多少錢。
3. 用實測數字取代本表的「假設值」分數。
4. 資安部門依第 9 章做供應商審查（資料流向、留存、合規）。
