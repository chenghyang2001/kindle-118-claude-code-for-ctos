# HANDOFF-POLICY：原型工具 → 生產環境交接規範

> K118《Claude Code for CTOs》第 3 章「市場全景」演練產出。
> 適用範圍：所有用 Vibecoding 工具（Lovable、Bolt 等）或其他快速原型方式做出、**想要上線或接觸真實客戶資料**的東西。
> 檢查項目參考書上第 8 章「生產就緒度稽核六大面向」與 `PROMOTION_CHECKLIST.md`、第 14 章 Mode A／B 分類。

## 1. 核心原則

1. **原型預設是要丟掉的**（書上第 14 章 Mode A：原型驗證，快速捨棄）。要上線就是「轉成 Mode B 生產級專案」，不是「原型直接部署」。
2. **交接的是「已驗證的需求」，不一定是程式碼**。原型程式碼品質太差時，正確做法是用 Agentic Coding 工具照原型行為重寫。
3. **沒有通過本規範的東西，不得部署到生產環境、不得連接正式資料庫、不得對外公開網址。**

## 2. 交接觸發條件（任一成立就要走本流程）

| 編號 | 觸發條件 |
| --- | --- |
| T1 | 原型要給公司外部的真實使用者使用 |
| T2 | 原型要連接正式資料庫或處理個資、付款資料 |
| T3 | 原型要接進公司既有系統（SSO、API、資料倉儲） |
| T4 | 原型存活超過 30 天仍有人在用（假設值：書上未給天數） |
| T5 | 有人提出「這個直接上線就好」 |

## 3. 交接條件（進入生產前必須全部滿足）

### 3.1 必要條件（Gate，缺一不可）

| 編號 | 條件 | 依據 |
| --- | --- | --- |
| G1 | 原型已證明需求成立（有使用者回饋或指標），並寫成 `PRD.md` | 書上第 5 章 PRD 五大區塊 |
| G2 | 程式碼已移進公司自己的 Git repo，有完整歷史 | 第 3 章可維護性 |
| G3 | 已用第 8 章六大面向提示詞完成稽核，產出 `AUDIT.md` | 第 8 章 |
| G4 | `AUDIT.md` 中 **critical 項目為 0**，high 項目都有負責人與修復日期 | 第 8 章評級 |
| G5 | 核心路徑測試覆蓋率 ≥ 50% | 第 8 章 `PROMOTION_CHECKLIST.md` |
| G6 | 已設定錯誤監控（如 Sentry） | 第 8 章 |
| G7 | 已有 `CLAUDE.md`，寫明架構決策、約定、What NOT to do | 第 14 章 Scaffold-First Step 1 |
| G8 | 有 CI 品質門檻（測試＋型別／lint 檢查，未過不得合併） | 第 14 章 Step 5 |

### 3.2 決策：沿用還是重寫

| 稽核結果 | 決策 |
| --- | --- |
| critical ≤ 2 且架構一致性評級為 medium 以上 | **沿用**：修掉問題後進入生產流程 |
| critical > 2，或架構一致性評級為 critical | **重寫**：以原型為「可執行的規格」，用 Claude Code 照 Scaffold-First 重做 |
| 資料模型沒有 migration、沒有外鍵（常見於 Supabase 控制台直接建表） | 至少重做資料層，先補 migration 再談上線 |

> 上表門檻（critical ≤ 2）是假設值，書上未規定，團隊可自行調整。

## 4. 交接檢查清單

交接時由原型負責人與接手工程師一起逐項勾選，結果附在交接 PR 中。

### 4.1 架構一致性

- [ ] 前後端、商業邏輯、資料存取有清楚分層
- [ ] 沒有重複的元件或複製貼上的大段邏輯
- [ ] 依賴的平台專屬功能（如原型平台的內建驗證）已列出替代方案

### 4.2 資安

- [ ] 沒有寫死在程式碼裡的密鑰、Token、密碼（已改用環境變數或密鑰管理服務）
- [ ] 曾經寫死的密鑰都已**作廢重發**（git 歷史裡還找得到）
- [ ] 每個 API 都有身分驗證與權限檢查
- [ ] 所有使用者輸入都有驗證；SQL 一律參數化查詢
- [ ] `.env`、憑證檔已列入 `.gitignore`

### 4.3 測試

- [ ] 核心路徑測試覆蓋率 ≥ 50%
- [ ] 登入、付款、資料寫入等關鍵流程都有測試
- [ ] 測試能在 CI 上自動執行

### 4.4 套件相依性

- [ ] 移除未使用的套件
- [ ] 已跑漏洞掃描（如 `npm audit`），沒有 critical 漏洞
- [ ] 套件版本已鎖定（lock 檔已進版控）

### 4.5 效能

- [ ] 沒有 N+1 查詢
- [ ] 列表類 API 有分頁
- [ ] 前端打包大小已量測並記錄基準值

### 4.6 資料模型

- [ ] 所有 schema 變更都有 migration 檔
- [ ] 常用查詢欄位有索引，關聯有外鍵
- [ ] 有備份與還原程序，且演練過一次

### 4.7 維運

- [ ] 錯誤監控（如 Sentry）已上線並收到測試事件
- [ ] 有基本的健康檢查端點與告警
- [ ] 有回滾方式（上一版可在 15 分鐘內恢復，假設值）
- [ ] `README.md` 寫明如何在本機跑起來

## 5. 責任人（RACI）

R＝負責執行、A＝最終負責（簽核）、C＝諮詢、I＝知會

| 步驟 | 原型負責人（PM／設計） | 接手工程師 | Tech Lead | 資安負責人 | CTO |
| --- | --- | --- | --- | --- | --- |
| 1. 提出交接申請、整理 `PRD.md` | R | C | A | I | I |
| 2. 搬進公司 repo、跑六大面向稽核（`AUDIT.md`） | C | R | A | C | I |
| 3. 決定沿用或重寫 | C | R | A | C | I |
| 4. 修 critical／high、補測試與監控 | I | R | A | C | I |
| 5. 資安檢查（第 4.2 節） | I | R | C | A | I |
| 6. 交接 PR 審查與簽核上線 | I | R | A | C | I |
| 7. 規範例外（未全過仍要上線） | I | I | R | C | A |

### 角色說明

- **原型負責人**：做原型的人，負責說清楚「它應該做什麼」，不負責修程式碼。
- **接手工程師**：之後長期維護的人；接手後就是這個服務的負責人（owner）。
- **Tech Lead**：交接是否通過的最終簽核者。
- **資安負責人**：對資安項目有否決權。
- **CTO**：只處理例外申請；例外必須寫明風險、補救期限，並記錄在交接 PR。

## 6. 交接流程（時間軸）

```
原型完成驗證
   │  觸發條件 T1–T5 任一成立
   ▼
① 提交交接申請（PRD.md）
   ▼
② 搬進公司 repo → 六大面向稽核 → AUDIT.md
   ▼
③ 決定沿用 / 重寫
   ▼
④ 修問題、補測試、補監控、寫 CLAUDE.md、接 CI
   ▼
⑤ 跑本文件第 4 節檢查清單 → 附在交接 PR
   ▼
⑥ Tech Lead + 資安簽核 → 上線
   ▼
⑦ 上線後 2 週追蹤錯誤率（假設值），原型平台上的舊版本下架
```

## 7. 原型平台的收尾

- 上線後，原型平台上的舊版本必須下架或設成私人，避免兩套系統同時被使用。
- 原型平台的帳號、API Key、資料庫連線在交接完成後全部撤銷。
- 原型的對話紀錄（prompt）可保留在 repo 的 `docs/prototype/`，當作需求來源參考。
