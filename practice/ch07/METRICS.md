# METRICS.md — Claude Code 採用成效指標

> 來源：K118《Claude Code for CTOs》第 7 章「衡量成效」。
> 兩個門檻（>2.0、>2.5）是書上的數字；標「假設值」的是本演練自訂。

## 1. 子代理對 session 比率（Subagent-to-Session Ratio）

| 項目 | 內容 |
| --- | --- |
| 健康值 | **> 2.0**（書上） |
| 想回答的問題 | 開發者是否把工作拆給子代理，還是把 Claude Code 當成單線聊天工具？ |
| 定義 | 一段期間內，平均每個 session 啟動幾個子代理 |
| 計算 | `SubagentStart 事件數 ÷ 不重複 session_id 數` |
| 資料來源 | hook 遙測：`SessionStart`（算 session）、`SubagentStart`（算子代理） |
| 計算週期 | 每週一次，看 4 週移動平均（假設值） |
| 偏低代表 | 還沒學會委派／平行化，回到第 16 章的平行化訓練 |
| 小心誤讀 | 子代理多不等於產出多；可能是單純「開很多子代理讀檔」。要配合交付指標（PR 合併數、週期時間）一起看 |

## 2. 開發者對代理比率（Developer-to-Agent Ratio）

| 項目 | 內容 |
| --- | --- |
| 目標 | **> 2.5**（書上） |
| 想回答的問題 | 每位開發者是否同時驅動多個代理，從「自己寫」轉成「指揮代理」？ |
| 定義 | 每位開發者每個工作日平均驅動的代理 session 數 |
| 計算 | `不重複 session_id 數 ÷ 開發者-日 數`（開發者-日＝某位開發者在某天有至少一個 session） |
| 為何用「開發者-日」當分母 | 直接除開發者人數，數字會隨統計天數變大，無法跨週比較。這個分母是本演練的詮釋（假設值，書上原文未在本機核對） |
| 資料來源 | `SessionStart` 事件的 `developer`、`session_id`、`ts` |
| 偏低代表 | 一次只開一個 session、等它做完；可導入 git worktree 多 session |
| 小心誤讀 | 開很多 session 但每個都被放棄，比率也會很高；要配合 `Stop` 事件看 session 時長 |

## 3. 指標生命週期檢查表

每個指標上線、檢視、廢除都走同一張表，避免「指標變成目標」（Goodhart 定律）。

### 3.1 上線前

- [ ] 寫清楚這個指標想回答的**一個**決策問題
- [ ] 定義、公式、資料來源寫進本檔
- [ ] 確認遙測只收中繼資料（不收提示詞與程式碼）
- [ ] 指定負責人
- [ ] 訂下第一次檢視日期（上線後 4 週，假設值）
- [ ] 預先寫好**廢除條件**（見 3.3）

### 3.2 定期檢視（每月，假設值）

- [ ] 數字還在影響決策嗎？過去一個月有沒有人因此做了什麼調整？
- [ ] 有沒有被「刷數字」的跡象（例如子代理暴增但 PR 數沒變）？
- [ ] 和交付成果（PR 合併數、週期時間、缺陷率）的相關性還在嗎？
- [ ] 資料品質：壞行比例 < 1%（假設值）

### 3.3 廢除條件（符合任一條就廢除或換指標）

| 條件 | 子代理/session | 開發者/代理 |
| --- | --- | --- |
| 已達標並穩定 | 全團隊連續 8 週 > 2.0（假設值） → 降為季度抽查 | 全團隊連續 8 週 > 2.5（假設值） → 降為季度抽查 |
| 不再驅動決策 | 連續 2 次月檢視沒有任何行動 | 同左 |
| 被刷數字 | 比率上升但交付指標持平或下降 | 同左 |
| 與成果脫鉤 | 和 PR 週期時間相關性消失 | 同左 |
| 工具改變使定義失效 | Claude Code 改了子代理機制或事件名稱 | 改了 session 計算方式 |
| 隱私疑慮 | 被用於個人績效排名 → **立即停用** | 同左 |

### 3.4 廢除後

- [ ] 在本檔標示「已廢除」與日期、原因
- [ ] 移除對應 hook 與儀表板
- [ ] 保留歷史資料 90 天後刪除（假設值）
