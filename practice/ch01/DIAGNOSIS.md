# DIAGNOSIS — CTO 原型與團隊瓶頸診斷

> K118《Claude Code for CTOs》第 1 章「CTO 的現實」演練產出。
> 來源標記：**【書】** = 書上（經 NotebookLM 摘要）明確提到；**【推論】** = 本演練依書中主軸推導，書上未逐字寫出；**【假設值】** = 書上沒有的數字。

## 本章核心論點【書】

1. AI 導入是**組織與注意力瓶頸**，不是單純的預算問題。
2. 成功關鍵在於把技術領導者**腦中的架構規範顯性化**（寫成 `CLAUDE.md` 這類 AI 與人都讀得到的文件）。
3. 不同規模的 CTO 面對的瓶頸不同，所以第一步也不同。

## 四種 CTO 原型

| 原型 | 團隊規模 | 核心瓶頸 | AI 導入第一步 |
| --- | --- | --- | --- |
| Solo CTO | 1 人～2 人【假設值】 | **個人頻寬限制**【書】：CTO 同時是架構師、開發者、維運，時間就是天花板 | 自己先用 Claude Code 接手重複性工作（測試、樣板、遷移），並把「自己腦中的規則」寫成第一版 `CLAUDE.md`，讓代理不必每次重講【推論】 |
| Small Team CTO | 3～10 人【假設值】 | **團隊做法分歧**【書】：每個人用 AI 的方式、提示詞、品質標準都不同，產出難以審查 | 建立**一份共用的 `CLAUDE.md`** 與 PR 審查規範，統一「AI 產出的程式碼怎麼驗收」【推論】 |
| Mid-Size CTO | 10～50 人【假設值】 | **CTO 注意力被稀釋、規範只存在少數資深者腦中**【推論】：CTO 不再能親自審每個 PR，知識傳遞靠口耳相傳 | 挑 3～5 人試點小組（呼應第 6 章），把架構決策、禁止事項顯性化成分層 `CLAUDE.md`，再由試點者擴散【推論】 |
| Scaling CTO | 50 人以上【假設值】 | **組織變革抗力**【書】：流程、資安、合規與既有習慣讓任何新工具推行緩慢 | 先建**治理 Harness**（權限、稽核、成本控制）與成效指標，讓資安／財務單位放心，再分批推廣【推論，對應前言「建構治理 Harness」】 |

> 註：NotebookLM 摘要明確列出的瓶頸只有三項（個人頻寬、做法分歧、組織變革抗力）；Mid-Size 的瓶頸、各原型的人數區間與「第一步」細節屬本演練推論，請對照原書修正。

## 團隊瓶頸診斷表（可勾選）

勾選符合現況的項目；**哪一區勾最多，就是你目前所處的原型與主要瓶頸**。

### A. 個人頻寬（Solo 型訊號）

- [ ] CTO 每週寫程式時間超過 50%【假設值門檻】
- [ ] 架構決策、code review、上線都只有 CTO 一人能做
- [ ] CTO 請假一週，產品進度就停擺
- [ ] 重複性工作（測試、樣板、資料庫遷移）沒有人能分擔
- [ ] 架構規則從沒寫下來，因為「反正只有我在看」

### B. 做法分歧（Small Team 型訊號）

- [ ] 團隊成員各自用不同的 AI 工具或不同提示詞
- [ ] AI 產出的 PR 風格不一致，審查時常為命名／錯誤處理爭論
- [ ] 沒有共用的 `CLAUDE.md` 或程式碼規範文件
- [ ] 同一類任務，有人用 AI 一小時做完、有人三天還在手寫
- [ ] 新人入職要靠「問人」才知道專案慣例

### C. 注意力稀釋與知識集中（Mid-Size 型訊號）

- [ ] CTO 已經無法親自看過每個 PR
- [ ] 關鍵架構知識只在 1～2 位資深工程師腦中
- [ ] 跨團隊的介面約定常被違反
- [ ] 想導入 AI，但不知道該從哪個團隊開始試點
- [ ] AI 使用狀況與成效沒有任何數據

### D. 組織變革抗力（Scaling 型訊號）

- [ ] 導入新工具需要資安、法務、採購多方核准
- [ ] 有工程師明確反對或懷疑 AI 產出的品質
- [ ] 沒有權限／稽核機制，無法回答「AI 動了哪些檔案」
- [ ] 無法預測 AI 工具的月成本
- [ ] 有多個 repo、多套 CI，規範難以一致套用

### 判讀

| 勾選最多的區塊 | 主要瓶頸 | 優先行動 |
| --- | --- | --- |
| A | 個人頻寬 | 先把自己的重複工作交給代理，寫第一版 `CLAUDE.md` |
| B | 做法分歧 | 統一 `CLAUDE.md` + PR 審查規範 |
| C | 注意力稀釋 | 試點小組 + 分層 `CLAUDE.md` + 開始量測 |
| D | 變革抗力 | 治理 Harness（權限、稽核、成本）先行 |

> 多區同分時，以**字母較前**的區塊優先處理（頻寬問題不解決，後面的規範與治理都沒人推）【推論】。

## 共通第一步

不論哪種原型，書中強調的共同起點都是：**把 CTO 腦中的架構規範寫下來**【書】。本資料夾的 `CLAUDE.md` 草案即示範此步驟。
